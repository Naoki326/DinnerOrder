## 1. 目标与验收场景

### 1.1 目标

自家使用的家庭工具（网页端、手机优先，非多租户产品）：家人在手机上**按餐槽预定今天的菜**，系统**按家人画像（人数/大小孩/忌口/爱吃/时令）生成菜与量的推荐**，家人看后**可换候选**，掌勺者拿到**汇总买菜清单**，历史记录**积累喜好与去重**。

### 1.2 验收场景（E2E 契约）

每个场景对应一条 Playwright 端到端（[#11](https://github.com/Naoki326/DinnerOrder/issues/11) 决议）；决策支撑对照见 §10。

| # | 场景 | 通过标准 |
|---|------|---------|
| **S1** | **主闭环：手机上 10 分钟内顶下一餐并拿到买菜清单** | 打开 app（无登录）→ 选中身份 → 首屏即见最近的未定餐槽大卡 → 点「给我推荐」→ 一键接受整餐 → 买菜清单页出现本餐聚合的食材与生重。全程 ≤ 10 分钟、无需任何说明文档 |
| S2 | 换菜 | 单道下钻可见 3 个候选，各带一句理由；候选列表标注忌口排除原因（如「白灼虾 — 小宝忌虾」）与「没做过」标记；「再换一个」在同一会话内累积排除已出示候选；「换一整套」生成新整套且可反悔回上一套 |
| S3 | 份量折算 | 菜单按用餐者名单显示每道菜生重：成人按菜谱成人份基准，小孩按出生年月现算年龄分带折算（6–10 / 11–13 / 14–17 岁） |
| S4 | 留量 | 晚餐餐槽可预定为「吃剩的」并引用前一餐菜单 → 被引用午餐的单道菜可标记留量、买菜量按系数（默认 1.5×）上浮 → 取消被引用的午餐时，晚餐槽提示并自动退回未定，事件留痕 |
| S5 | 反馈与冷藏 | 菜单阶段单道可点踩 + 快捷标签（太油/太甜/量太多等 3–4 个）；餐后回顾常驻入口（不弹窗）可点踩/点赞 + 同套标签；任一用餐者点踩后该菜 14 天内不进推荐与候选 |
| S6 | 外部补位与转正 | 家庭池某荤素位候选 <3 时外部菜谱补足并显著标「没做过」；该菜上桌后掌勺者可在餐后回顾点「转正」，改写差异后进入家庭库与推荐池 |
| S7 | LLM 降级 | 断网/超时/schema 校验连败后，界面给出纯规则拼餐的「简化推荐」并显著标记；LLM 恢复后可随时换一整套 |
| S8 | 买菜清单 | 跨餐聚合同一食材生重合计，附生熟换算参考；可加手工行；改餐后清单标记过期、手动重算（勾选按食材继承、手工行保留）；清单可归档 |
| S9 | 视图模式 | 设置中三选一视图模式（A 下一餐大卡默认 / B 掌勺者紧凑流 / C 长辈小孩极简），设备本地存储；三视图数据模型与操作语义一致 |
| S10 | 部署可用性 | launchd 开机自启、崩溃自动拉起；经 nginx 子路径（如 `/dinner/`）与直连 `http://<host>.local:8787` 两种方式均可用；每日 SQLite 热备文件存在且滚动保留 |

### 1.3 Out of scope（边界）

多家庭/多租户/SaaS 化；库存/冰箱/剩菜精细管理（留到下顿只体现为做菜量上浮）；医疗级营养管理；买菜配送/自动下单集成；早餐的菜谱推荐与采购（早餐现成品/冻品直接热，不进推荐管线）；外网访问与内网穿透（仅内网，[#4](https://github.com/Naoki326/DinnerOrder/issues/4)）；买菜清单菜场现场体验的进一步打磨（按原型 v1 现状实施，上线后按使用反馈另起努力）。

## 2. 功能规格

### 2.1 餐槽与预定（#2、#7）

- 模型是**按餐槽预定**，不是周期制：任何时刻可把「当前时刻之后的某一餐」（日期 × 午/晚）从「未定」变为「已定」；未定的餐 app 不追踪、不提醒、不填充。早餐不进模型。
- 主界面「下一餐优先」单列滚动：打开即见最近未定餐槽大卡，往下今天晚餐、明天……每天至多午/晚两卡。不做周历。
- 定餐 = 换菜，**同一编辑器**：整餐推荐一键接受为默认；下钻单道可换 / 可删、底部加菜。
- 预定支持**取消**（已定 → 未定，历史留痕）。取消被「吃剩的」引用的午餐时提示 + 引用方晚餐槽自动退回未定。
- 推荐按「打开 app 时现算」设计，不做定时预生成。
- 权限：不做。任何身份可看/可定/可换/可评。M1 不处理多人并发编辑（后写赢）。

### 2.2 整餐推荐（#9）

- **显式触发**：用户点「给我推荐」按钮，打开餐槽不自动生成。
- 结构由家规定，推荐默认值而非硬约束，定餐时可手动加减菜：基线 **2 荤 1 素 1 汤**，每 ±1 大人 → ±1 道菜（M1 公式写死，家规可调）。
- 管线详见 §4。

### 2.3 换菜（#2、#9）

- 单道替换一次给 **3 个候选**，各带一句理由；「再换一个」走 LLM，同一换菜会话内被换掉的 + 已出示过的候选**累积排除**，池干后放宽；LLM 失败降级为规则排序 top3。
- 「换一整套」重新生成整餐，**可反悔**回到上一套。

### 2.4 身份（#2）

- **无登录**：常驻身份切换器（头像），同机随时切换，操作归属当前身份。家庭 Wi-Fi 即门禁，app 不加口令。

### 2.5 反馈与餐后回顾（#2、#9）

- 菜单阶段：单道菜点踩 + 可选 3–4 个快捷标签（太油/太甜/量太多类）。不做自由文本、不做整餐级反馈。
- 餐后回顾：饭后餐卡常驻「吃后感」入口（不弹窗不推送），点踩/点赞 + 同套快捷标签。
- 反馈**正式进推荐管线**（#9 推翻了 M1 仅记录的旧表述；机制见 [ADR-0005](../adr/0005-preference-rules-not-weights.md)）：点踩 → 该菜**冷藏 14 天**（家规可配；任一本餐用餐者点踩即触发，布尔不叠加），期内不进推荐与候选，到期自动解除；点赞与快捷标签进 30 天反馈文本摘要作软信号，**零数值权重**。餐后回顾的读者是掌勺者。

### 2.6 留量（#2、#7）

- 表达方式：晚餐餐槽预定为「吃剩的」→ 引用前餐（午餐）菜单 → 对午餐的**单道菜**标记多做、量上浮（绿叶菜不留的现实 → 留量是单道级）。
- 上浮生效条件 = 留量标记 **∧** 有效引用存在；系数默认 1.5×（家规可配），计入买菜量。

### 2.7 买菜清单（#7、#8）

- **物化实体**，状态：进行中 / 已归档。
- 行两种：**聚合行**（跨已定餐槽同一食材生重合计 + 生熟换算参考）与**手工行**（掌勺者临时加，不属于任何菜谱）。
- 改餐 → 清单标记**过期** → **手动重算**（重算时勾选状态按食材继承、手工行保留）。
- 形态按原型 v1 实施不再打磨（家人第一轮反馈无修改要求，#8）。

### 2.8 菜谱库（#3）

**双层结构（核心决定，[ADR-0006](../adr/0006-two-tier-recipe-library-with-promotion-gate.md)）：**

- **家庭菜谱库** = 推荐池唯一来源：只收家里做过且掌勺者确认（转正）的菜。
- **外部菜谱池** = 素材层，不直接进推荐池，仅当家庭池某荤素位候选 <3 时补位（标「没做过」）。来源三个：
  1. **HowToCook**（Anduin2017/HowToCook，Unlicense 公有领域）——许可干净，首选打底源；
  2. **下厨房爬取**——无开放许可，自家私用、风险自知接受，来源字段如实标「爬取」；只轻量抓家常热榜或用现成小数据集，不搞全站爬；
  3. **LLM 生成**——走同一条草稿管线。

**冷启动**：外部池批量打底 150–300 道家常菜（混合口味：按「家常热度 + 忌口排除」筛，不按菜系；菜系仅作参考 tag），家里慢慢转正沉淀，不做一次性口述冲刺。食材字典同步冷启动：WS/T 554 附录 A 互换表 + HowToCook 导入归一。

**导入工具执行细节**（开发会话交付项）：HowToCook 导入脚本、下厨房轻量取数、模糊份量（「适量」）导入/转正时一律由 LLM 重标到成人份克数。

**菜谱 schema（精简核心集）：**

- 身份：菜名 + 别名（家人叫法）；荤素类型 荤 / 素 / 汤（汤分荤素）。
- 食材与份量：每项 = 食材（指向食材字典）+ **成人份生重克数基准** + 可缩放规则 + 生熟换算锚点（WS/T 554 互换表）。
- 推荐标签：口味**封闭五标签** 甜/辣/酸/咸鲜/清淡（多选）+ 菜系参考 tag（导入时 LLM 初打、转正时掌勺者校对）；适季月份；忌口关联（食材清单推导 + **隐性忌口**标记，如蚝油含贝类）；难度耗时三档 快手(<20min)/中等/费事。
- 治理：状态机 草稿 → 转正 → 退役（退役不进推荐、历史保留）；来源（口述/HowToCook/爬取/LLM 生成）；编辑留痕。
- 做法步骤自由文本，掌勺者参考用，**不进推荐管线**。

**转正机制**：外部菜谱被预定上桌 → 餐后回顾里掌勺者点「转正」→ 可口述差异（多点辣/不放蒜）→ LLM 在原菜谱上改写成家里版本 → 进家庭库 + 推荐池。

**治理**：掌勺者编辑、全家提议（提议归属当前身份）、掌勺者确认生效；无真鉴权，靠约定 + UI 引导。

### 2.9 家人画像（#7、#6）

- 字段：大人/小孩、男/女、出生年月（小孩必填——折算系数查表时现算年龄自动分龄）、忌口[]、爱吃[]。
- **忌口 = 硬过滤**：任一本餐用餐者命中（含隐性忌口经食材字典「含」指针展开）即从推荐/候选排除；掌勺者手动加菜只提示不阻止。
- **爱吃 = 软加分**：混合粒度清单（食材或具体菜），不分档，进推荐 prompt。

### 2.10 视图模式（#8）

- 设备本地的界面偏好（与「当前身份」同级的轻量设置，不进画像、不跨设备共享）：A 下一餐大卡（**默认**）/ B 掌勺者紧凑流 / C 长辈小孩极简。
- 三套视图共享同一数据模型与操作语义（换菜/留量/回顾行为一致），仅呈现不同。

## 3. 数据模型（#7）

实体关系终稿（词汇见 [`CONTEXT.md`](../../CONTEXT.md)）：

```
家人 Member（大人/小孩、性别、出生年月、忌口[]、爱吃[]）
    │   忌口 ──→ 食材字典（硬过滤，隐性忌口经「含」指针展开）
    │   爱吃 ──→ 食材 或 具体菜（软加分，不分档）
    ▼
餐槽 MealSlot（日期 × 餐次［午/晚］，未定 / 已定）
    ─1:1（已定时）→ 菜单 Menu
         ├─ 用餐者名单快照（默认全员、可临时改）
         ├─ 菜品 ×N：→ 菜谱（家庭/外部；草稿→转正→退役）+ 份量 + 留量标记
         └─ 另一形态：「吃剩的」→ 引用前餐菜单的留量菜品
              （上浮生效 = 留量标记 ∧ 有效引用）
    菜单一切变化 → 留痕（append-only 事件流）
    菜品 × 家人 → 反馈（点踩/赞 + 快捷标签）

份量 = 菜谱成人份生重基准 × Σ用餐者折算系数 × 留量上浮
       （折算系数按 WS/T 554 年龄×性别分带，内置数据表；LLM 不进数值路径）
家规 = 单例配置（2荤1素1汤基线、±1大人±1道、上浮默认 1.5×、
       去重窗口 7 天、冷藏期 14 天等，全部可调）

买菜清单（物化实体：进行中/已归档）= 聚合行（同食材生重合计+生熟换算参考）+ 手工行
    改餐 → 标过期 → 手动重算（勾选按食材继承、手工行保留）

食材字典 = 规范名 + 别名 + 时令月份 + 隐性忌口「含」指针（四处共用：
           忌口、爱吃、菜谱食材、买菜清单聚合）
```

关键语义决议：

1. 忌口/爱吃建模**不对称**（硬过滤 vs 软加分，见 §2.9）。
2. 份量**纯规则查表**（[ADR-0004](../adr/0004-portion-lookup-not-llm.md)）：可解释、离线、零成本、错好查；LLM 只在导入/转正时做「适量→克数」重标，不进运行时数值路径。
3. 历史 = **留痕事件流**（append-only，[ADR-0007](../adr/0007-append-only-meal-history.md)）：预定（接受整餐推荐）、换单道、换一整套、取消各记一条；「最近吃过」去重直接查事件流；事件携带 LLM 调用元数据 `{模型名, prompt模板版本, 耗时, 降级?}`（#9 可观测性要求；模板进代码库 git 管版本）。
4. 留量挂**引用有效性**：取消被引用的午餐 → 提示 + 引用方晚餐槽自动退回未定（事件留痕）。
5. 折算系数内置数据表来自 WS/T 554—2017（见 §5）。

## 4. 推荐管线（#9，架构见 [ADR-0001](../adr/0001-llm-selects-not-generates.md)）

```
用户点「给我推荐」（显式触发）
① 规则引擎（取数全部前置，LLM 零工具调用）：
   忌口硬过滤（本餐用餐者名单，含隐性忌口展开）
   → 家庭菜谱池按荤/素/汤位 × 时令月份检索，每位 6–8 道
   → 某位家庭池候选 <3 → 外部菜谱池补足（#3 导入筛法，标「没做过」）
   → 去重双档：同菜 7 天硬排除（家规可配）；近 7 天已吃列表进 prompt 供主料软避让
   → 聚合近 30 天反馈摘要（点踩/赞 + 快捷标签；冷藏菜已在入口排除）
② qwen3.8-flash 单次纯 completion（温度 0.7、超时 30s、strict json_schema）：
   prompt = 候选池紧凑 JSON（id/菜名/主料/位/近30天次数/来源）
          + 画像/爱吃/反馈摘要/近 7 天已吃（自然语言文本）
          + 家规结构指令（结构由规则定，LLM 只填位）
③ 输出 {菜品:[{菜谱id, 理由一句话, 来源:家庭/外部}]}
   —— 无份量（后端查表：成人份 × Σ折算系数）、无留量标记（掌勺者事后标记触发重算）
```

- **检索-选择式**：LLM 只从规则检索池中选与搭配，不自由生成、不调工具循环；输出仅菜谱 id，幻觉无处发生（取舍理由见 ADR-0001）。
- 换菜候选也走 LLM（同位替换 3 候选各带理由、会话内累积排除，见 §2.3）。
- **降级链**：网络重试 1 次 → strict schema 失败转 `json_object` + Zod 校验重试 1 次（[#5](https://github.com/Naoki326/DinnerOrder/issues/5) 决议）→ 仍失败给纯规则拼餐的「简化推荐」（时令 + 荤素结构 + 去重 + 爱吃排序），界面显著标记；**不用缓存菜单**（会过时成毒数据）。
- **API key**：`.env`（chmod 600）存放 DashScope key；排除出 Time Machine 与 SQLite 热备双通道；不自动轮换，手动换 + 重启。完整请求/响应仅在 `DEBUG=1` 时落 `data/logs/`（随 .env 排除出备份）。
- LLM 客户端：官方 `openai` npm 包 → 百炼 OpenAI 兼容端点（[#5](https://github.com/Naoki326/DinnerOrder/issues/5) findings：qwen3.8-flash 大陆直连、strict `json_schema`、家用月成本个位数人民币；备选 GLM-5.3-Flash，仅 `json_object` 档）。
- **地理位置不进管线**：时令即食材字典月份表，按自家菜场实情录入（#9）。
- MCP：工具接口按 MCP 形状设计（名称/描述/JSON Schema 参数），**M1 进程内直调**；M2 先把时令食材（外部数据、独立更新）MCP 化，份量/营养计算这类纯计算留进程内（#5、ADR-0001）。

## 5. 内置数据资产（#6，[findings](https://github.com/Naoki326/DinnerOrder/blob/research/health-portion-basis/research/health-portion-basis.md)）

**直接进规则表（一手来源，可程序化转录）：**

1. **每人每天各类食物量**：成人平衡膳食宝塔 2022（1600–2400 kcal 五层全数值）；儿童 6–10 / 11–13 / 14–17 岁学龄儿童宝塔 2022；学龄前 2–5 岁妇幼分会宝塔（OCR 值，**入库前复核一次**）。
2. **餐次占比**：早 25–30% / 午 35–40% / 晚 30–35%（WS/T 554—2017 §3.3）→ 规则表存「全天量 × 餐次占比」，天然支持留量上浮。
3. **逐餐逐年龄带量表**：WS/T 554—2017 表 1（分年龄×性别能量）、表 3/4（每餐克数）、附录 A 生熟/同类互换表（50g 米≈米饭 110g/馒头 80g 等）——份量折算系数与食谱↔买菜换算的唯一依据。
4. **搭配锚点**（进 prompt 背景，不进硬规则）：每天 12 种/每周 25 种；午晚餐「2–3 种蔬菜 + 1–2 种动物性食物 + 1 种豆制品」；深色蔬菜过半。

**不进规则表（家规/提示词自由度）**：荤素个数随人数公式、留量上浮比例、口味偏好——均无权威依据，属家规。「N 荤 N 素」公式只写进 prompt 与家规配置。

**时令食材**：无权威开放数据 → 手工维护 30–40 种常买食材 × 12 月小表（按自家菜场实情录入），存食材字典。

## 6. 技术栈与存储（#11，取舍理由见 [ADR-0002](../adr/0002-ts-monorepo-react-hono-sqlite-single-process.md)、[ADR-0003](../adr/0003-runtime-configurable-base-path-for-nginx.md)）

| 层 | 选型 |
|---|---|
| 语言/仓库 | TypeScript 全栈；pnpm workspace 两包 `server/`（Hono + better-sqlite3 + 领域逻辑）、`web/`（React）；共享类型由 server 导出 |
| 前端 | React 18 + Vite（`base: './'` 相对资产引用）；hono/client（类型层）+ TanStack Query v5；React Router v7（library 模式）约 4 条路由（主界面 / 买菜清单 / 回顾 / 画像·菜谱管理）；手写 CSS——全局设计 token + CSS Modules，直接搬原型样式语言（`--accent`、荤/素/汤三色、圆角、中文优先字体栈），不用 Tailwind |
| 后端 | Hono 4 + @hono/node-server；zod + @hono/zod-validator 入参校验；`openai` npm 包接百炼兼容端点 |
| 存储 | SQLite + better-sqlite3 + 手写 SQL；~30 行迁移执行器（`server/migrations/` 编号 .sql，启动时按序执行并记录版本）；无 ORM |
| 工件 | **单进程前后端一体**：一个 Node 进程监听高位端口（默认 `0.0.0.0:8787`），`/api/*` 走 Hono、其余 serveStatic 前端 Vite build 产物；开发时 Vite dev server proxy `/api` |
| 路径 | **BASE_PATH 运行时注入**（ADR-0003）：服务端读环境变量（默认 `/`），Hono 按其挂载，页面注入 `window.__APP_CONFIG__.basePath`；前端 Router `basename`、API 前缀、PWA manifest `start_url`/`scope` 均从注入值推导。同一构建产物可挂 `/`、`/dinner/`、任意端口，无需重打包 |
| 测试 | Vitest（server 单测 + API 集成）+ Playwright（§1.2 每验收场景一条端到端，薄层） |
| PWA | 仅 manifest + 图标 + meta（可安装主屏尽力而为），**不做 Service Worker** |
| Node | 24.x LTS（下限 22），Mac mini 用 Homebrew 安装 |

**数据目录布局**要容纳 `backups/` 与 `data/logs/`（#4 输入）。

## 7. 部署与访问（#4 + #11 细化）

- **硬件**：Mac mini 常开（Node ≥ 20 硬门槛天然满足，实际跑 24 LTS）。
- **运行时**：launchd 直跑（LaunchAgent + 开机自动登录），崩溃自动拉起；一个 plist 指 `node dist/server/index.js`。不用 Docker Desktop、不用 pm2。
- **访问**：仅内网。两条路：
  1. **nginx 正面**（宿主机已有 nginx）：子路径反代，`location /dinner/ { proxy_pass http://127.0.0.1:8787/; }`（尾斜杠剥前缀 → `BASE_PATH=/`）；或不剥前缀写法（→ `BASE_PATH=/dinner`）。HTTPS/门禁跟随宿主 nginx，app 不感知。无 WebSocket，无需 upgrade 配置。
  2. **直连兜底**：`http://<host>.local:8787`（mDNS 已配好；路径无关化使直连自动按根路径跑）。
- **HTTPS**：不做（已知悉：无 Service Worker/离线壳；Android Chrome 只有标签页快捷方式；iOS「添加到主屏幕」仍可用）。日后可无痛补 mkcert，不影响本决议。
- **备份**：Time Machine 整机 + app 每日 SQLite 热备（`sqlite3 .backup` 到 `backups/`，按日滚动保留 N 份），双保险、零云依赖。
- **LLM 出站**：Mac mini 出站 443 直连 DashScope，家宽无限制，无需代理。

## 8. 原型与家人反馈结论（#8）

- **资产**：分支 `prototype/main-ui` → [`prototype/main-ui.html`](https://github.com/Naoki326/DinnerOrder/blob/prototype/main-ui/prototype/main-ui.html)（单文件、假数据、内存态，main 不收；d03e299 三变体 + 8ff84db 设置切换）。实施时从该分支搬样式 token 与交互形态。
- 原型已埋的关键决策：定餐=换菜同一编辑器；单道 3 候选（含忌口排除原因展示）；换一整套可撤销；留量 ×1.5；餐后回顾=点踩+快捷标签；无登录常驻身份切换；家规 2 荤 1 素 1 汤（可加减菜）；买菜清单聚合/手工行/过期重算/生熟换算参考。
- **家人第一轮反馈（已收齐）**：① 掌勺者——三视图全部保留为「视图模式」设置项、默认 A（已落原型 8ff84db）；② 其余家人——无异议、无修改要求。买菜清单维持 v1 形态。
- 原型底部的黑色胶囊变体切换条是**评审工具**，不是产品功能，实施时去掉。

## 9. 实施里程碑建议

- **M1（本 spec 全量）**：核心闭环全部功能；工具进程内直调（MCP 形状的接口、无 MCP 进程）；外部池冷启动导入（HowToCook 150–300 道 + 份量重标 + 食材字典归一）；家规公式写死为单例默认值；多人并发后写赢。
- **M2（后续，不阻塞验收）**：时令食材工具 MCP 化（stdio server + Inspector 调试）；（可选）mkcert HTTPS 升级全功能 PWA；多人并发编辑冲突处理（如需要）。
