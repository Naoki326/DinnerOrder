# 版式与视图模式正交：视口宽度判据 + 手动覆盖

界面上有两个**设备本地、正交**的呈现偏好，都存 localStorage、都不进任何接口入参与留痕：

* **视图模式**（ADR 之外的既有决定，spec §2.10）：A 下一餐大卡 / B 掌勺者紧凑流 / C 长辈小孩极简
  ——决定**用哪一套界面**；
* **版式（Layout，本 ADR 新增）**：手机版 / 平板版——决定**这一套摆成几列**。

平板上 A/B/C 都能用、各自变成宽屏摆法；手机上 A/B/C 仍是单列。两者可以各自选、互不干涉
（在 iPad 上把版式钉成手机版，不影响视图模式；把视图模式切成 B，不影响版式）。

## 判据：视口宽度 ≥ 900px 用平板版

```
layout = preference === 'tablet' ? 'wide'
       : preference === 'phone'  ? 'narrow'
       : matchMedia('(min-width: 900px)').matches ? 'wide' : 'narrow'
```

判据**只有一处**（`web/src/layout.tsx`）：页面/组件一律 `useLayout()` 读派生值，不得自己调
`matchMedia`——否则阈值会在多处漂移。阈值 `TABLET_MIN_WIDTH` 导出为单一常量，设置面板文案与
E2E 都引用它。

选 900 而不是 768：iPad 竖屏的现代机型（1024）与 iPad mini 竖屏（744）之间，宁可让 744 走
手机版（单列看着不空），也不要让 800px 的桌面窗口拿到一半的双列。**阈值可以再谈**，但改它要
一起改 E2E 的 project 尺寸与设置面板文案，属于要显式决定的改动。

## 为什么不用 UA / 设备类型探测

* UA 不可靠：iPadOS 默认把 Safari 伪装成 Macintosh，桌面浏览器也能伪装；
* `pointer: coarse` 会把触屏笔记本、带笔的平板一律判成平板；
* 「这是什么设备」本来就不是这个决定要回答的问题——要回答的是**这块屏现在的宽度够不够摆两列**，
  而视口宽度是能直接观察到、且在浏览器里立刻可验证的那个事实。

## 为什么不用纯 CSS 媒体查询

纯媒体查询做不到「手动覆盖优先于宽度」：设置里的「手机版 / 平板版」必须同时作用于**布局与弹层**。
只按媒体查询分支会让手动覆盖只管布局不管弹层，出现「平板版页面 + 手机版底部抽屉」的错配。
所以宽窄两版由壳上的 `data-layout` 决定（组件读 `useLayout()` 的派生值挑形态），
而不是 `@media`——**当前版式**也有了一个稳定、可断言的锚点（`app-shell[data-layout]`）。

## 降级

* `matchMedia` 不可用（旧浏览器、隐私模式）：降级为**手机版**，而不是白屏；
* `localStorage` 不可用（隐私模式）：偏好当次会话仍然生效，界面不报错。

与 `viewMode.tsx` / `identity.tsx` 既有的 `try/catch` 处理同口径。

## 三条判据

* **难逆转**：`body { max-width: 480px }` 这条写死在全局、不区分设备的约束被拆掉了，
  容器宽度改由壳按版式控制。拆了之后再想回到「一套手机布局」需要动六页的摆法。
* **无上下文会困惑**：未来读到「同一个页面有两套列数、还靠一个 localStorage 值切换」，
  会以为代码写了两遍——而这是「同一套东西两种摆法」的有意选择。
* **真实取舍**：纯媒体查询（零 JS、但手动覆盖失效）vs 按偏好分支（能覆盖、要一处锚点）——
  选了后者，因为「iPad 上想用手机版」是家人明确可能有的诉求。

## 与既有 ADR 的关系

* **不改 ADR-0002（单进程前后端一体）与 ADR-0003（BASE_PATH 运行时可配）**：`data-layout` 是
  **运行时属性**，不影响「同一份构建产物挂 `/` 或 `/dinner/`」这条线。
* **不改 ADR-0004（份量纯规则查表，LLM 不进数值路径）**：版式不碰任何数值。
* **服务端零改动**：版式是纯前端呈现偏好，与 `viewMode` / 当前身份一样不进任何接口入参、不进留痕、
  不建表、不做迁移。
