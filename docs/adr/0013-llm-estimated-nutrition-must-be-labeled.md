# 允许 LLM 估算食材营养，但必须逐行标为估算、且「合计偏低」的信号不能丢（部分修正 ADR-0004）

食材字典新录入的食材**没有营养数据**（迁移 012 的《中国食物成分表》第 6 版只覆盖当时用到的
142 条，其中刻意不录 23 条）。本 ADR 允许在**录入食材**时让 LLM 给出四项营养的**估算值**，
按普通营养行落进 `ingredient_nutrition`，但**出处必须写清是估算**。

## 这个决定部分修正 ADR-0004

ADR-0004 的标题就是「份量纯规则查表，LLM **不**进数值路径」，理由是「可解释（每个克数都能回溯到表与系数）
／离线可用／零调用成本／错了好查好改」。本 ADR 让 LLM 产出的数字进入**营养合计**，
这是运行时数值路径的一部分——**ADR-0004 在这条上是松动的，必须显式记下来**，
否则后来者会以为代码坏了。

**ADR-0004 没被碰的部分**：份量（克数）仍然纯规则查表，一个 LLM 数字都不进。这是本 ADR 的边界，
也是最该守住的那一半——克数进锅里，营养只是读数。

## 为什么与 ADR-0001 不冲突

ADR-0001 把 LLM 钉在「只选不生成」，「含」提议（ADR-0012）也守了同一条。营养估算**看起来**又破了一次，
但它与「含」提议的**风险结构完全不同**：

* 「含」指针错了 → 家人的**忌口硬过滤**漏放或误排，是**行为**错误，传播面是全库；
* 营养估算错了 → 一个**读数**偏了一点，行为不变，且**读的人自己知道这是估算**（见下）。

所以两者的处置也不同：含指针**不许凭空生成目标**，营养**允许估算但必须标注**。

## 决定

**一、估算值按普通营养行落库，但 `source` 必须自证是估算。**
`ingredient_nutrition.source` 的既有纪律是「逐行写清平台食物名与原始数值」（012 文件头）。
估算行沿用同一列、同一纪律，但内容改写成「LLM 估算（模型 X）：参照 <最接近的成分表条目>」——
**不给估算行第二条列、也不给它第二个表**（表多了就有第二个真相）。判定「是不是估算行」
靠 `source` 的固定前缀，**不靠新列**。

**二、「合计偏低」的信号不能因为估算而消失——`partial` 的判据要改。**
这条是本 ADR 里最容易做错的一条。现状：`partial` / `missingIngredients` 的判据是
「这一项有没有营养行」，界面据此写「XX 没算进上面的数字，所以合计偏低」。
一旦缺数据的食材都有了估算，这个信号会**自动变空**——而差额并没有消失，只是从
**已知的缺失**变成了**不知道的误差**。所以：

* `missingIngredients` 保留原义（**完全没有**数据），行为不变；
* **新增**「含估算值」的报法：估算的食材要在界面上**能单独被数出来并点名**，
  与之对应的措辞是「这几项是估算的，数字是参考」而不是「没算进合计」；
* `partial` 的语义从「有食材没数据」扩成「**合计不是全由成分表读数构成**」——
  有估算项时为真，且要能区分是**缺数据**还是**估算**（两种情况的措辞与后果都不一样）。

**三、估算绝不静默覆盖成分表读数。**
已经有人工编纂行（`source` 指向成分表）的食材，**不允许**被估算改写。要改只能人来改。
这条是 012「宁可缺失也不编数」在打补丁之后的残余，仍然有效：**人不编数，LLM 估算，但两者分得清。**

**四、估算值必须由人确认后才落库。**
与「含」提议（ADR-0012）、导入（ADR-0011）同一形状：LLM 产出的是**预填**，
录入表单里给四项一个可编的预填值 + 出处说明，人点保存才落库。
**LLM 不可用时四项留空、不拦保存**（缺数据是既有的合法状态）。

**五、估算不进数值路径的其它入口。**
只用于**新录入的食材**。批量重标（`import-library` / 转正链路）不因此获得估算能力——
那是 ADR-0006 的门槛管的事，本 ADR 不碰。

## 三条判据

* **难逆转**：一旦估算值进了 `ingredient_nutrition` 并与人工编纂行**同表同列**，
  事后想把它们分开就要按 `source` 重新分类全表。放宽之后再收紧，等于要么删掉全部估算、
  要么给表加来源列并重建。
* **无上下文会困惑**：未来读到「一个 LLM 猜的数字，和《中国食物成分表》的读数并排存在同一张表、
  且一起进合计」，第一反应一定是「谁把 012 的口径搞坏了」。
* **真实取舍**：手工录 + 必填 source（012 原义，权威但每条要查表）vs 估算进合计（快，
  但合计变成混合数）。选了后者，代价是 `nutritionSource` 那句口径必须重写
  ——它现在写的是「食材营养取《中国食物成分表》平均值」，有估算项之后**这句话会是假话**，
  所以注记也要按「本次读数里有没有估算项」分两种措辞。

## 被否决的备选

* **估算值存起来但不进合计**（单独展示、只做参考）：口径最干净，但等于保留了两套数字，
  界面要说清「这个数算进去了、那个数没算」，比直接算进去更绕。
* **不回填、继续留缺**（012 原义）：缺口会持续变大——本次录入功能一上线，
  每录一条新食材就多一条缺口。
* **给估算开第二个表 / 第二列**：表多了就有第二个真相，且合计要 union 两处。
* **沿用 012 手工录入 + 必填 source**：不破任何口径，但每条食材都要人工查一次成分表，
  实测代价高到会让「录一条新食材」这件事没人愿意做。

## 实施注记（issue #38 落地，2026-10-03）

三条本 ADR 没写、但落地时必须定的口径（都已成代码，写在这里免得后来者重新推）：

1. **数字由模型给，但「参照了哪条成分表条目」必须落在池子里。**
   本 ADR 只说 source 要写「LLM 估算（模型 X）：参照 <最接近的成分表条目>」，没说数字从哪来。
   实施取的口径是**模型给数字、参照条目过池内校验**（`llm/nutrition-estimate-schema.ts` 的
   `resolveNutritionEstimate`）：对不上池子就**整条不可用**（重试后降级），而不是「换个参照」或
   「照收」。理由与「含」提议的「越界丢该条」不同：那边丢的是一条建议，这边丢的是**整行的出处**
   ——出处要是编的，这一行就是假证据。
   池子只含**非估算行**：估算以权威读数为参照；拿估算当估算的参照会让出处链条变成「估算的估算」。
2. **四项 all-or-nothing。** 只有部分项有值时整块不算数（路由层 Zod 拦，报 400 并说清
   「四项要么全给、要么不给」）；四项全空的唯一表达是**整个 `nutrition` 字段不传** = 暂缺。
   落库行永远是四项齐全的一行——「半行营养」在合计里没法解释（那一项算半份还是缺？）。
3. **「改食材」里四项原样提交不算一次改动**（不写台账，报 409 `no_changes`）。
   判据只比四项数字、**不比参照条目**：重估时参照可能换成另一条读数，但那不改变这一条的读数。
   与「改食材」其余四个字段同一口径（ADR-0012「决定五」）。

### 补记：「决定五」的边界（改食材这条路也在估算能力之内）

「决定五」原文说估算「只用于**新录入的食材**」，它的真意是**不给批量重标开估算口子**
（`import-library` / 转正链路不因此获得估算能力）——那是 ADR-0006 的门槛管的事。

**「改食材」（`PATCH /api/ingredients/:id`）接受 `nutrition` 是本 ADR 范围内的**，理由有两条：

* 本票 AC 明写「已有成分表读数的食材**不被估算覆盖**（服务端拦下，返回明确错误，不是静默忽略）」
  ——「覆盖」这个动作只可能发生在**改**这条路上（新录入的食材本来就没有读数可覆盖）。
  不支持 PATCH，这条 AC 就没有可验的对象。
* 「改食材」的既有语义就是「按需补增量」（CONTEXT：「别名、时令月份、「含」指针、营养都是
  **事后按需补的增量**」）。录入时没填营养、后来补上，与后来补个别名是同一件事。

**批量重标那条路仍然没有估算能力**（`import-library` 与转正都不调 `estimateNutrition`）——
这才是「决定五」要守住的边界。
