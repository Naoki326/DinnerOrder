# 掌勺者手写的菜直接进家庭库，外部数据仍须转正

掌勺者在菜谱库页面**手写录入**的新菜以 `status='active'`（家庭库 + 推荐池）入库、`source='oral'`，**不需要先做过**。

## 这个决定部分修正 ADR-0006

ADR-0006 说家庭库「只收家里做过、掌勺者确认转正的菜」，转正门槛是「家里做过、家人吃过」。本 ADR 对
**掌勺者手写这一条路**开口：他录的菜**没做过**就进家庭库与推荐池。

**ADR-0006 对外部数据的门槛完全不变**：HowToCook / 下厨房爬取 / LLM 生成（`howtocook`/`scraped`/`llm`）
进来的菜仍然是草稿，仍然必须上桌、仍然必须经掌勺者确认转正才进家庭库。本 ADR 是**部分修正**，
不是推翻——读 ADR-0006 的人不该认为代码违反了它：那条门槛防的是外部数据，不是掌勺者。

## 理由

ADR-0006 的门槛是为了挡住**外部数据**：质量参差、许可风险、家里没验证过。掌勺者自己写的菜不适用
这条理由——他既是录入者，也是那个要确认它的人。「家里做过」这个信任信号被他的**身份**替代了。

反过来说，若坚持让他先做一顿才能把菜录进库，「今天想做个新花样」就得先写 SQL 或者去跑那个面向
外部数据的导入 CLI——而那道菜根本不是「外部菜谱」。这正是本 ADR 要解掉的困境。

## 三条判据

* **难逆转**：改了「进推荐池」的门槛。放宽之后再收紧，掌勺者写的菜会被赶出推荐池。
* **无上下文会困惑**：未来读到「手写的菜没吃过就在推荐池里」会以为代码坏了。
* **真实取舍**：严格守门槛（一律先做过）vs 信任掌勺者（他的身份就是那个确认）。

## 派生判定：「还没上过桌」

「家里新录入、还没被任何一餐吃过」是**派生的**——没有转正记录 ∧ 没有任何一餐的菜单引用过它。
它不是 `recipes` 上的一列，也不是 `source`（转正过的外来菜也有转正记录，手写菜没有；两者都不该
按 `source` 判）。上桌吃过之后标记自动消失，不需要手动关。

它与外部菜的「没做过」（判定源 `status='draft'`）**判定源不同、措辞刻意不同，不得在同一渲染点混用**。
