# 食材字典首次开放写入路径：人可增改，删仅在零引用时，LLM 只从字典里挑「含」的目标

食材字典（`CONTEXT.md` 的「食材字典」）此前是**只读**的：`GET /ingredients` 是唯一接口，
条目只能从离线导入管线（`server/scripts/import-library.ts` + `library/collectors.ts`）写入。
本 ADR 开一条写入路径——**录入食材 / 改食材 / 删食材**（词汇见 `CONTEXT.md` 的「食材字典维护」），
并把「含」指针的提议交给 LLM，但**限定它只能从字典现有条目里挑目标**。

## 为什么值得一条 ADR

字典是**全库唯一受控表**，忌口硬过滤、爱吃加分、菜谱食材、买菜清单聚合四处共用同一个基数
（`CONTEXT.md`「食材字典」）。在这张表上开写入路径，等于给「受控」二字开了一个口子——
未来读到「字典能被界面写」，第一反应会是「那受控在哪」。这个口子必须写在能被搜到的地方。

同时它**难回头**：`ingredient_aliases.alias` 是全局 PRIMARY KEY（一个叫法只能指向一个食材），
所以删掉一条食材会**永久释放一个名字**给未来复用；且 9 张表引用它，其中 5 张是 `NO ACTION`
（`recipe_ingredients`、`member_avoid`、`member_loves`、`exchange_items`、`grocery_items`），
有引用时物理删**不可能**。

## 决定

**一、拒绝自由文本食材，只走字典。** 菜谱编辑器搜不到时，不做「敲个名字就这样存」的逃逸通道，
而是**就地转新建**（搜不到 → 提示「字典里没有对得上的食材」→ 引导录入该食材）。理由：

* 自由文本行**绕过忌口硬过滤**——家人对莴笋忌口时，手敲的那行不会被排除；
* 买菜清单会**分裂成两行**（「莴笋」与字典里的「莴笋」），而 `CONTEXT.md` 明说买菜按字典聚合、
  细粒度条目**分列不合**（「基础条目（裸名）」词条的「猪肉 vs 猪排骨」同理）。

保受控表完整的代价是录入时要多点两下，这个代价被接受。

**二、录入的必填项只有规范名。** 别名、时令月份、「含」指针都是事后按需补的增量。
理由是摩擦决定字典会不会被用，而这三项都是**有上下文的增量**——人是在「家里人忌贝类」的那一刻
才想起蚝油要挂贝类，不是在建「蚝油」的那一刻。这与既有口径一致：**不录时令 = 四季有售**
（002 起就有，013 迁移把「新增条目全部不写月份」作为显式判断执行过），不是缺录。

**三、加与改都不设身份门槛，但改要留痕。** 谁都能录、谁都能改（ADR-0009 已撤掉掌勺者限制，
加一条「莴笋」不是决定谁吃饭）。但**改条目是追溯性变更**：把「莴苣」改名成「生菜」，
所有引用它的菜谱、买菜清单、家人的忌口显示全跟着换说法。所以「改」走留痕，
与 `recipe_edits`（014 迁移）同一形状——**改的是内容，不是这条食材从哪来**，正与
`CONTEXT.md`「修订」词条对「转正」的区分同构。

**四、删只在零引用时允许。** 9 张引用表一处都没提到它才能物理删；有引用时唯一的路是改名。
判据只有一条：**有没有人用它**。不是权限问题而是完整性——放行「反正还没人用」之外的删除
就会把受控表架穿。

**五、「含」指针由 LLM 提议、人确认，且 LLM 只从字典现有条目里挑目标。**
这是 ADR-0001「LLM 只从检索池中选、不自由生成」在食材上的原样复用，**不是对 ADR-0001 的修改**：

* 提议是**预填而非写入**（与转正链路同一形状，见 ADR-0011 对「信任的根」的区分）；
* LLM **不凭空生成食材名**——字典里没有「贝类」这条基础条目时，它只能报「没有可挂的目标」，
  由人先建「贝类」；
* LLM 不可用时这个框照样手填、不拦保存（对照「简化推荐」的降级精神）。

之所以不让 LLM 自由生成：说错「生抽含麸质」对一个不忌麸质的家庭无害，说错一个真忌的项就是事故，
而这个错误的传播面是**全库的忌口硬过滤**。ADR-0001 的边界在这里恰好也是安全边界。

## 被否决的备选

* **自由文本食材行**（见「决定」一）。看起来省事，实际把忌口过滤与买菜聚合两处一起架空了。
* **并条工具**（选两条食材 → 整体搬引用 → 被并者消失）：这才是根治，但要动 5 张表并回答
  「并完两边的忌口/爱吃冲突」，是独立一票的体量，而它解决的问题（两条都被用了之后才发现重复）
  在这个量级下罕见。当下替代：**改名字**。
* **只允许改名、不允许删**：太紧。刚建 10 秒、还没被任何菜谱用上的错条目，「改个名」在语义上是错的
  （它本来就不该存在），而且错名字会**永久占住别名表**，挡死以后真要建的那条。
* **给「含」指针设 LLM 自由生成**：见「决定」五的传播面理由。
* **录入时要求填全三件套**（别名 + 时令 + 含）：把别名与时令变成必填，只会让人绕过字典去写自由文本，
  等于**从后门把「决定」一作废**。

## 边界（本决定不管什么）

* **菜谱那条受控路一点没动**：ADR-0006 的外部数据门槛、ADR-0009/0011 的两条信任口子都没被碰。
  本 ADR 只给**食材字典**开写入路径，不给菜谱开。
* **`PANTRY_STAPLES`（家里要有）不因此改变形态**：它仍是一个**厨艺常识的封闭名单**
  （`domain/ingredients.ts`），不随字典增删自动变——新录的调料不会自动成为「家里要有」。
* **品种仍不入库**：013 已定「黑猪/土猪这类品种无需追踪、不建 parent_id 层级」，本 ADR 不重开。
* **新旧条目在推荐里同权**：新食材默认无时令月份，因此**拿不到时令加分**（时令是排序不是过滤，
  `domain/ingredients.ts` 的 `seasonalIngredientIds`），但不会被排掉。宁可拿不到加分，也不给假信号。
