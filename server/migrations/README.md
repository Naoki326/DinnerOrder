# 迁移（migrations）

`server/migrations/` 下按 `<三位版本号>_<描述>.sql` 命名（如 `001_members_and_ingredients.sql`），启动时由
`src/db/migrate.ts` 按版本号升序执行，已执行的记录在 `schema_migrations` 表；每个文件一个事务，失败回滚后下次启动重试。
数据资产（折算系数、推荐量、互换表）也写在迁移里：它们与 schema 一样需要「何时入库、来源是什么」的留痕，
而 per-row 的 `source` 列就是那页出处。

- 不要修改已执行过的迁移文件，追加新编号即可（append-only 的 schema 历史）。
- 现有版本：
  - `001_members_and_ingredients` —— 食材字典（规范名 + 别名）与家人画像（大人/小孩、性别、出生年月、忌口、爱吃），
    含本家常用食材与真实家人种子（M1-02 / #14）。
  - `002_recipes_and_meal_slots` —— 家庭菜谱库（成人份生重基准 + 可缩放规则 + 生熟换算锚点 + 治理状态机）、
    食材字典扩充（时令月份 + 隐性忌口「含」指针）、餐槽与留痕事件流（append-only，ADR-0007），
    含家庭常做菜与两道刻意留出的状态样本（M1-03 / #15）。
  - `003_portion_engine` —— 份量引擎的规则资产：成人能量锚点、WS/T 554 分带折算系数
    （系数 = 分带能量 ÷ 同性别成人锚点，两条列都落库）、逐带参考能量（表 1）、
    各人群每天推荐量（成人宝塔 2022 + 学龄前宝塔）、附录 A 生熟/同类互换表（M1-04 / #16）。
    **数据来源逐行写在 source/note 里**：学龄前宝塔数值与 2–3/4–5 档系数是官方图 OCR、
    尚未对照原图复核；成人能量锚点（2250/1800 kcal）来自 DRIs 纸书、书未开放。
    学龄儿童宝塔（6–10/11–13/14–17）**不录**：它的分带与 WS/T 554 的分带对不齐，
    两套并存会让「这个孩子吃多少」出现两个打架的答案（见 003 文件头）。
  - `004_external_recipe_pool` —— **外部菜谱池种子**（M1-05 / #17）：九道题标 `status='draft'` 的
    家常菜（荤/素/汤齐备，覆盖 HowToCook / 爬取 / LLM 三个来源）。
    存储形态有意复用草稿态而不是另建一张表：外部池不是独立实体，
    而是「还没转正的那些菜谱」——ADR-0006 的状态机就是这个语义，#19 的批量导入落同一处。
    种子**刻意混入**会命中本家忌口的材料（辣椒 / 豆瓣酱 / 蚝油类），让「忌口硬过滤」在补位这条
    路径上也有真实样本可测。数量只够拿通「某位家庭池 <3 时补位」这条路，批量打底是 #19 的活。
  - `005_import_toolchain` —— 导入工具链的三件数据资产（M1-07 / #19）：`recipes.cuisine`（菜系参考 tag，
    单值列 + CHECK 白名单）、食材字典扩充（中餐常客：牛肉类/水产/酱料/香料）、时令手工表补齐到 40 种
    （报表 `seasonGrid()` 的输入）。同时重建 `recipe_ingredients`：`adult_grams` 的 CHECK 从 `> 0`
    放宽为 `>= 0`——**0 = 模糊份量待 LLM 重标**（存量行为 NULL 的 `source_quantity` 列留给采集到的份量原文）。
  - `006_feedback_and_family_rules` —— **反馈与家规**（M1-08 / #20）：
    `dish_feedback`（菜品 × 家人 × 那一餐：点踩/赞 + 时间）+ `dish_feedback_tags`（快捷标签，CHECK 封闭四值：
    太油/太甜/量太多/量太少）+ `family_rules`（**单例**配置：冷藏期天数默认 14、餐次截止时刻午 14 / 晚 21）。
    反馈**不挂 meal_events**：留痕 append-only，而反馈可以改主意（点错重按）——两种语义各自一张表。
    家规表本票只放自己需要的可配值；推荐管线的其余常量留给 #26 统一收口（代码里标了 TODO）。
  - `007_leftover` —— **留量（M1-10 / #22）**：**不再建 `family_rules`**——006（#20）已经建好那张
    单例表并种下 id=1 那行，这里只 `ALTER TABLE family_rules ADD COLUMN leftover_uplift`
    （默认 1.5，CHECK 1–5）给它补上留量上浮系数（家规是同一份配置，两张同名表只会让「家规读在哪」分叉）。
    另加 `meal_events.leftover_menu_slot_id` 的索引（002 只落了列）。引用关系与单道留量标记本身都是
    002 早已备好的形状（`meal_events.leftover_menu_slot_id` / `meal_event_dishes.keep_leftover`），
    本票不改这两处的表结构、只落值。
  - `008_recipe_promotions` —— **转正台账**（M1-09 / #21）：`recipe_promotions`（菜谱 × 掌勺者 ×
    转正瞬间：口述差异原文、菜系前后值、LLM 调用元数据）。转正**不加实体、不加状态**——
    ADR-0006 的双层库只是 `recipes.status` 的状态机（draft → active），本表补的是总纲 §2.8
    要求的「**编辑留痕**」：转正是唯一一次由 LLM 直接改写既有菜谱行的操作，改完要能回答
    「谁按谁的口述改成了什么、原来是什么样」。与 `dish_feedback` 同理不挂 `meal_events`：
    那张 append-only 表记的是**菜单的变化**，转正记的是**菜谱库的变化**。
    另种一条 **本票自己的待重标样张**（`pending_relabel_ribs`：主料排骨 0 克 + 其余项克数齐全，
    克数待 LLM 重标；#19 台账点名请 #21 把待重标标出来，而 004 的种子全是确切克数）。
    它是一条**新菜**——不改 004 的任何行（生数据纪律）——所以它不是「生数据」，是外部池的样张。
    不种任何转正记录：历史由真实使用产生。
  - `009_grocery_list` —— **买菜清单**（M1-11 / #23）：`grocery_lists`（进行中/已归档、过期标记 +
    原因**结构**、聚合餐数；**同时只能有一份进行中**用局部唯一索引钉死）+ `grocery_items`（聚合行 /
    手工行共用一张表，靠 `kind` 区分；`needs_relabel` 标记导入期 0 克「待重标」项）+
    `grocery_item_sources`（聚合行的来源：哪一餐的哪道菜，存 slot_id/recipe_id 而不是渲染好的字符串）。
    总纲 §2.7 明写清单是**物化实体**：物化的不是聚合算法（那是读已定餐现算的），而是聚合的**结果**
    ——勾选态、手工行、过期标记这三样不属于任何一餐、也不属于任何菜谱，现算没有地方存它们。
    过期原因存**结构**：`stale_reason` 枚举短码（`menu_changed` / `cancelled` / `set_undone` /
    `family_rules_changed`）+ `stale_slot_id`（哪一餐；家规类为 NULL，两列由 CHECK 钉成对）；
    界面那句中文由前端现拼——存渲染好的中文会让「改文案」变成「改历史数据」，
    而且「今天午餐」这种相对叫法会随时间漂移。本文件已在交付前随 #23 评审修复轮改过（尚未合入 main）。
  - `010_member_soft_delete` —— **家人可删（家人管理票）**：只给 `members` 加一列
    `deleted_at TEXT`（NULL = 在用）。删除是**软删除**：删掉的家人从列表消失、不再进用餐者名单、
    忌口/爱吃不再生效，但 `meal_event_diners` 的姓名/头像快照与 `dish_feedback` 的行都原样保留
    （硬删会经 006 的 `ON DELETE CASCADE` 把反馈带走，而那正是「历史积累喜好」的输入）。
    不建索引：家人是个位数行的家庭小表。
  - `011_cook_per_meal` —— **掌勺者按餐指定**（需求变更）：掌勺者从 `members.is_cook`（001 的
    家人全局标记）收窄为「家里**通常**做菜的那位」，真正的判定落到每一餐——给 `meal_events`
    加 `cook_member_id` + 当时的姓名/头像快照（`cook_member_name` / `cook_member_emoji`）。
    落在 append-only 事件流上而不是新开一张表：掌勺者是「这一餐由谁做」，属于菜单变化的一部分
    （ADR-0007；与 007 给同一张表加 `leftover_menu_slot_id` 同一先例）。因 `meal_events` 的
    append-only 触发器让 UPDATE/DELETE 都非法，**加列**是唯一合法的 schema 变更。三列要么都空
    （未指定）、要么都齐（跨列 CHECK 钉死），存快照不回头查 members——家人被软删后历史菜单里
    也照旧读得出当时的名字。未传 `cook` 时**按上一餐继承**（本餐槽之前最近一餐里当前生效的那位），
    一路往前没有才回落 `is_cook`（读侧另下发 `MealSlot.cookDefault`）。**不改 `members.is_cook`**：
    它是最底一层缺省（开 app 默认身份 + 掌勺者无上一餐可继承时的回落），本票同时把它做成可改
    （`ProfilePatch.isCook`）。
  - `012_meal_nutrition` —— **每餐营养指标（营养与食谱票）**：新建一张数据资产 `ingredient_nutrition`
    （食材 × 每 100 g 可食部四项：能量 kcal / 蛋白质 / 脂肪 / 碳水）**逐行带 `source`**。
    数据源是《中国食物成分表（标准版）》第 6 版，逐条经中国营养学会 / 中国疾控中心营养与健康所
    「食物营养成分查询平台」`nlc.chinanutri.cn/fq/` 取数，`source` 里写清平台食物名与原始数值
    （kJ 已按 ÷ 4.184 换算成 kcal）。**142 条**（外部池 266 道菜与家庭菜谱用到的全部食材里
    平台能查到的 140 条 + 水/开水 2 条），按食材项出现次数计覆盖 **90.9%**；
    **平台查不到对应条目的 23 条不录**（蚝油 46 次、八角 24、香叶 22「…），**宁可缺失也不编数**
    ——读接口把它们报成「没有营养数据」而不是 0 克营养。
    **不落每餐营养实体**：营养 = Σ(`portionOf` 给的逐食材本餐克数 ÷ 100 × 本表营养)，每次现算
    （与份量同一口径、同一时钟，spec §177「纯计算留进程内」）。
    食谱**不建表**：`recipes.steps`（002）已是真数据，本票只在它旁边加了只读的
    `GET /api/recipes/:id/recipe`（步骤 + 食材清单）。
  - `013_ingredient_base_entries` —— **食材字典补录「扁平 + 三件套」**（issue #28）：
    ① **裸名基础条目**（猪肉/鸡肉/芝麻/米饭/蒜粉/姜粉/椒盐粉/白葡萄酒/芥末/小苏打）——
    菜谱的粗粒度语言（「猪肉 200g」）有处落，买菜清单不再缺项；
    ② **`ingredient_contains` 指针连部位**（猪排骨→猪肉、白芝麻→芝麻、干辣椒→辣椒…）——
    忌口沿**既有**的展开机制向上传播（推荐与换菜两处过滤零改动自动生效），方向单向；
    ③ **品种子类不入库**（黑猪/土猪不建行）：品种可随意替换，不是要追踪的维度。
    另补一批**错别字与口语写法**的别名（耗油→蚝油、肉→猪肉、温水→水…），收录面限于
    story 7 的错别字 + issue 头部范围点名的裸名 + 报告里 ≥2 次的口语写法；**长尾真缺项不补**
    （印度综合香料粉/白芷/酥油…仍留在导入报告的 unmatched 清单里，是刻意留着的欠账）。
    **时令表本轮无新增**：现有 40 条全是蔬菜/菌菇，新增的 10 条都是四季常售的肉/禽/主粮/调料，
    按 002/005 的口径「不录月份 = 四季有售」（给四季常售的东西填月份等于把时令信号抹成常量）。
    **不建 parent_id 层级**（部位与品种是两个维度，层级化后「忌子类不忌基础类」的语义分叉必须回答）——
    将来若真要按品种追踪，须另立 ADR。
  - 迁移里只种**规则资产与字典**，生数据（餐槽、菜单、推荐）一律不种：推荐永远现算不落库（总纲 §4）。
- 种子数据写在迁移里（而不是启动时补种），这样测试 harness、E2E 的文件库、生产库三条路径拿到的是同一份初值。
- 执行器自身的行为由 `src/db/migrate.test.ts`（临时目录 fixture）覆盖；本目录内容由 `src/db/schema.test.ts` 与
  各 API 集成测试覆盖。
